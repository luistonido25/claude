Session 1 — The sabotage lab: break it five ways, watch it die

≈ 2 hours

You can't design error handling for failures you've never seen. So you're going to cause every classic failure deliberately, in a controlled setting, and study the corpse in History. Rules of the lab: one sabotage at a time, always undo before the next one, and write down the exact error name Make shows you.

Session 2 — Error handlers: Ignore vs Resume vs Break, and the incomplete executions queue

≈ 1.5 hours

Make gives you five error-handling directives. You met them briefly on Day 3; today you use the three that matter daily. The mental model: Ignore = drop this bundle and move on. Resume = substitute a fallback output and continue as if it worked. Break = park the run in the incomplete executions queue and (optionally) auto-retry — the right answer for transient failures.

Session 3 — Build M4, part 1: the standard error route on every portfolio scenario

≈ 2 hours

Here's the practical pattern real Make consultants ship: every important scenario gets the same error route — log one row to a central Errors sheet, fire one Telegram alert, then Ignore (or Break, for flaky modules) so the scenario stays alive. Boring, repeatable, and exactly what a client pays for.

Session 4 — Build M4, part 2: the 18:00 daily digest + packaging

≈ 1.5 hours

Instant alerts are for fires; a daily digest is for management. One scheduled scenario reads today's rows from the Errors sheet and sends a single Telegram summary at 18:00 — the kind of quiet, cheap monitoring a client actually keeps paying for.

⚠️ Undo every sabotage before you log off

Run the checklist: Leads tab renamed back, Google connection reauthorized, Record ID mapping restored, Airtable Source field back and re-mapped, seeded test rows deleted from the Errors sheet. Then flip scenarios OFF. A half-sabotaged scenario left ON is exactly the silent failure this whole day taught you to prevent.
