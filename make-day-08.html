Session 1 — Airtable setup and why naive two-way sync loops forever

≈ 1.5 hours

Two-way sync is where amateurs burn a month of operations in one weekend. System A changes → sync writes to B → B's "watch" trigger fires → sync writes back to A → A's trigger fires → forever. Today's whole design exists to break that loop. First, build the Airtable side.

Session 2 — Direction 1: Sheets → Airtable, guarded

≈ 2.5 hours

The pattern per contact: look up in ledger → not found? create → found but changed? update → found and identical? stop. Every module past the lookup only runs when there's real work, which is exactly what keeps operations low.

Session 3 — Direction 2: Airtable → Sheets, same guard

≈ 2 hours

Mirror image, one new trick: the Airtable trigger really can watch for edits (thanks to the Last Modified field), so this direction is event-shaped. The hash guard is what stops direction 1's writes from echoing back.

Session 4 — The test matrix, proof, and packaging

≈ 1.5 hours

A sync you haven't tested in all four directions is a rumor, not a deliverable. Run the matrix with Run once on each side (don't schedule both ON until the matrix passes).

📦 Deliverable of the day

[M3] Sync A and [M3] Sync B working and verified, the sync_ledger data store populated, two blueprints + canvas/ledger/History screenshots + operations-meter screenshot in your portfolio folder, and a journal entry with the test-matrix results and the loop-prevention explanation in your own words.

⚠️ Both scenarios OFF before you close the laptop

Two-way syncs are the #1 quota burner: two scheduled scenarios polling forever. After the endurance check, flip both switches OFF. Also: if the sync ever misbehaves, clear the sync_ledger (Data stores → Browse → delete all) and blank the Airtable ID column before re-running — a stale ledger causes ghost updates.
