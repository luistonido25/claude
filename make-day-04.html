Session 1 — Custom webhook: your scenario gets a public URL

≈ 1.5 hours

Everything so far ran on a schedule. A Custom webhook makes a scenario instant: Make gives you a unique URL, and any system that can send an HTTP request (a website form, another tool, a script) fires your scenario the moment data arrives. This is the trigger behind most real client work.

Session 2 — Telegram bot: alerts in your pocket

≈ 1 hour

Telegram bots are free, instant, and take ten minutes to wire — which is why they're the default "ping the owner" channel in the automation world. You need two things: a bot token (the credential) and your chat ID (the address).

Session 3 — Validation router + the happy path

≈ 2.5 hours

Production rule: never trust inbound data. The router splits valid leads from broken ones; the happy path cleans the data with Day-2 functions before anything touches the sheet. Build order: router first, then the valid route module by module, then the error branch.

Session 4 — Three-payload test, proof, packaging

≈ 1.5 hours

A build you haven't tried to break isn't finished. Three payloads: one perfect, one broken, one ugly. Use reqbin or the curl line — for the autoresponse, put YOUR own address (or a you+test@gmail.com alias) in the email field so you actually receive it.

⚠️ Webhook URLs are public

Anyone who has your webhook URL can POST to it — there's no login in front. For training that's fine; for clients, mention (and journal now) the defenses: keep the URL out of public code and screenshots, validate payload shape with the router exactly as you did today, and for real security add a shared-secret field to the payload and filter on it. Rotating a leaked webhook = delete the hook in Webhooks and create a fresh one.
